## 主要发现

### 1. 零视觉区分 —— 全库无 callout

整个 vault 172 个文件中，**0 个使用了 Obsidian callout**（`[!info]`、`[!warning]`、`[!tip]`、`[!question]` 等）。所有内容——状态说明、风险提示、操作建议、结构化定义——都以相同的基础 markdown 呈现。

**影响：** 读者无法通过视觉快速区分"这是状态信息"、"这是风险"、"这是操作建议"。每个文件都需要从头到尾阅读才能找到关键信息。

**例：** `市场调研报告与商业规划路线图.md` 中风险表前有一段"待验证假设"的文字说明，内容关键但与其他正文完全同构，容易被扫过。

### 2. 零可视化 —— 无图、无流程图、无架构图

全库无：
- 无 Mermaid 图表（架构图、流程图、时序图）
- 无 Excalidraw 手绘图
- 无嵌入式图片

**影响：** 数据模型、事件流转、用户旅程等天然适合可视化的内容全部以文字描述，理解成本高。

**缺少可视化但需要的内容（建议区域）：**
| 文件 | 建议加图 | 
| :--- | :--- |
| `03-数据模型/01-规范与模板/事件流转规范.md` | Mermaid 时序图 |
| `03-数据模型/00-总览/数据模型总览.md` | Mermaid 类图 / ER 图 |
| `04-本地录入与分析链路/02-流程定义/` | 用户操作流程图 |
| `07-测试验收/绩效报告.md` | 数据看板图（可选） |

### 3. 知识点卡片视觉单调

`02-课标与知识体系/02-国家课标知识树/` 下的 89 张知识点卡片格式统一但视觉单一：每张卡片由 31 行 frontmatter + 约 10 个分段（每个 2-3 行，纯列表）组成。

**当前格式：**
```
## 定义

段落文本

## 适用范围

- 条目
- 条目
```

**建议：**
```
## 定义

> [!info] 核心定义
> 段落文本

## 关键能力

> [!tip] 学生应能
> - 能识别
> - 能应用
```

用 callout 包裹每个部分，阅读时一目了然。

### 4. 宽表格影响窄屏阅读

| 文件 | 列数 | 影响 |
| :--- | :---: | :--- |
| `05-结果视图/学生端-*.md` | 7 列 | 窄屏需横向滚动 |
| `00-项目总控/竞品分析报告.md` | 5 列 | 可接受 |
| `00-项目总控/市场调研报告.md` | 5 列（风险表） | 可接受，但文本长 |

**建议：** 宽表格可加 Obsidian 的 `%%` 注释列或折叠到 `| 知识点 | 详情 |` 双列方案。

### 5. 整体结构：一致性红利已经吃完了

一致性是优点也是缺点。所有文件都是：
```
Frontmatter
# 标题
## 板块
### 子板块
- 列表项
```

没有变异就没有焦点。当每一页看起来都一样时，读者无法建立"这个文件哪里重要"的心智模型。

## 设计哲学建议

> **一个原则：** Obsidian 的 callout 和 Mermaid 不是装饰，是**信息层级工具**。
>
> 当一页中：
> - `[!info]` 表示**定义和状态**
> - `[!warning]` 表示**风险和约束**
> - `[!tip]` 表示**最佳实践和建议**
> - `[!question]` 表示**待验证假设**
>
> 读者无需逐字阅读，即可通过颜色和图标定位到需要关注的内容。
